# Skill — section assembler

## Purpose

Write the Business Requirements Document. Pull content from each artifact
for its designated chapter. Write in plain English for a non-technical
audience. Embed Mermaid diagrams with captions. Reference business rules
by ID. Flag gaps and low-confidence items inline where they appear.

This skill produces the final human-readable deliverable of the entire
reverse engineering pipeline.

---

## BRD document structure

Write the BRD in this chapter order. Each chapter has a defined source
artifact and writing instructions below.

```
brd.md
├── Cover page
├── Table of contents
├── 1. Executive summary
├── 2. System overview
├── 3. System inventory
├── 4. Data model and definitions
├── 5. Business rules catalogue
├── 6. Process descriptions
├── 7. Component architecture
├── 8. Error handling and recovery
├── 9. Gaps and assumptions register
└── Appendices
    ├── A. Full data dictionary
    ├── B. Program pseudocode reference
    └── C. Diagram index
```

**Paragraph 1 — System purpose**

what the system does at a business level.

**Paragraph 2 — Scale and complexity**

- Number of programs (batch vs online)
- Lines of code (total)
- Number of business rules extracted
- Number of data entities
- Number of files and databases accessed

**Paragraph 3 — Key findings**
Summarise the most significant findings:
- Most critical business rules (top 3 by rule set)
- Most complex programs (by complexity score from Logic Agent)
- Unstructured flow hotspots (programs with GO TO / ALTER)
- Data sharing patterns (most widely shared copybooks)

**Paragraph 4 — Gaps and limitations**

before BRD sign-off.

## Writing style guide

Apply these rules throughout the entire BRD:

- **Audience:** Business analysts, architects, product owners — not COBOL developers
- **Tense:** Present tense — "The system validates..." not "The system validated..."
- **Voice:** Active — "The program reads the file" not "The file is read by the program"
- **COBOL terms:** Always explain on first use — e.g. "copybook (a shared COBOL data definition file)"
- **Field names:** When mentioning a field name in body text, use its business-readable form followed by the COBOL name in parentheses — e.g. "account balance (`ACCT-BALANCE`)"
- **Rule references:** Always include the rule ID — e.g. "the credit limit rule (BR-001)"
- **Confidence flags:** Never omit them — use ✓ for confirmed/high, ⚠ for medium/low
- **Gap references:** Always link to the gap ID — e.g. "see GAP-001 in Chapter 9"
- **Diagrams:** Every embedded diagram has a figure number, a title, and a 1–3 sentence caption below
- **Tables:** Prefer tables over bullet lists for structured data
- **Paragraphs:** 3–6 sentences. No walls of text. No one-sentence paragraphs.

## Error handling

| Condition | Action |
|---|---|
| Program narrative missing from logic_artifact | Use `{PROGRAM-ID} is a {subtype} program.` as placeholder, log `warning` |
| Diagram file not found for embedding | Note `(diagram not available)` in caption, log `warning` |
| Rule set has no confirmed/high rules | Write section with medium/low rules, add prominent SME review notice |
| Chapter source artifact is missing | Write chapter header + `Content unavailable — {artifact} not found.` |
| gaps_register.md is missing | Generate inline from gaps_register.json, log `warning` |
| Entity has no description in data_artifact | Use `No description available.` and flag for SME review |
